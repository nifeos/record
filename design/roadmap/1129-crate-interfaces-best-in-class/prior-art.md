# Prior art: how other projects review an interface before they promise it

An appendix to [the milestone](../1129-crate-interfaces-best-in-class.md).

Each source below was fetched and read on 2026-11-25 (UTC), except where a line says "recalled".

| project | what it did | what this block takes | where this block differs |
|---|---|---|---|
| The Rust library team's Libz Blitz, 2017 ([the announcement](https://internals.rust-lang.org/t/rust-libz-blitz/5184)) | Raised sixteen key crates to 1.0 quality in one year. Per crate: a lead opened a thread, evaluators compared the crate to the API Guidelines and listed its deficiencies, the write-up was posted for public comment, the library team reviewed it in a meeting, and the lead filed discrete issues. Crates were evaluated only with their authors' consent. | One crate at a time against one checklist; a written evaluation; findings filed as discrete items. | It measured each crate against the guidelines, not against rival crates. This block adds named, measured comparators. |
| The [Rust API Guidelines checklist](https://rust-lang.github.io/api-guidelines/checklist.html) | 54 items in eleven groups: naming, interoperability, macros, documentation, predictability, flexibility, type safety, dependability, debuggability, future proofing, necessities. Each item has a code, such as `C-GOOD-ERR` or `C-SEALED`. | Every item, marked per crate with its code. | The checklist is a floor for any crate; this block uses it as one axis of nine. |
| The Rust library team's API change proposals ([the feature lifecycle](https://std-dev-guide.rust-lang.org/development/feature-lifecycle.html)) | A proposal is an issue in `rust-lang/libs-team` with a sketch of the API. The library API team accepts it when it is optimistic the change will pass its final comment period, and may still reject the feature at stabilization. | A review of the interface before the implementation is built on it. | The proposal reviews one addition to one library; this block reviews whole crates and what they share. |
| Tokio 0.3 and 1.0, 2020 ([0.3](https://tokio.rs/blog/2020-10-tokio-0-3), [1.0](https://tokio.rs/blog/2020-12-tokio-1-0)) | 0.3 shipped as a 1.0 beta, "an opportunity to validate the changes before stabilizing them". It removed pre-1.0 dependencies, `bytes` and `mio`, from the public interface, dropped trait methods few implemented, and merged and renamed feature flags. 1.0 promised five years of maintenance and three years before any 2.0. Neither post describes a formal API review. | A public dependency on a crate that has not reached 1.0 is itself a finding. Pre-release tags as the place to validate a change. Feature names settled before 1.0. | Tokio's validation was use by its ecosystem over two months; these crates have no users yet, so the comparison stands in for that use. |
| embedded-hal 1.0, released in January 2024 (the date recalled) ([the announcement](https://blog.rust-embedded.org/embedded-hal-v1/)) | In the works since 2020. It removed traits that generic drivers could not use, notably timers, and moved serial traits to `embedded-io`. Every error exposes a kind from one fixed set, with `Other` for the rest, and every error type implements `Debug`. Async, bus sharing and `nb` went to companion crates. | The error-kind convention as one candidate for the shared error decision. Removing what cannot be made right before 1.0, rather than shipping it. | It is one trait crate with many implementers; these are many crates with one maintainer each. |
| The Fuchsia API Council ([its charter](https://fuchsia.dev/fuchsia-src/contribute/governance/api_council)) | Every change to the API surface needs an API-Review+1 from a council member before merge, beside code review; a larger change starts as an RFC. An API joins the SDK only with a ready customer and after calibration. The area's member decides, the council as a whole is final, by rough consensus. | One reviewer who did not write the code signs off on every interface change. A published interface needs a customer: here, the measured demand. | The council is standing; this block is a review run once before the first publish of each crate. |

Not used: rustls's preparation for a stable release. No source describing a pre-1.0 interface
review there was read for this block, so nothing here rests on it.
